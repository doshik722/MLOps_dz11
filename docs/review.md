# Ревью предложения о постоянной привязке диалога

Постоянную привязку диалога к Pod при указанных условиях не принимаю. Если A начинает обработку через 3 секунды, а свободная B пересчитывает префикс за 0,8 секунды, для нового запроса предпочтительна B. Предварительная разница составляет 2,2 секунды до начала следующего этапа. Это оценка при заданных условиях, а не измеренное ускорение полного ответа. Нужно сравнивать ожидаемое время до первой содержательной части с учётом очереди, prefill, передачи контекста и текущей загрузки. Кеш — один из факторов выбора, а не основание игнорировать перегрузку.

До допуска нового запроса нужны свежие running/waiting по каждой реплике, p50/p95 ожидания и TTFC, доля отказов, длины запросов, hit/miss и стоимость пересчёта. Сигналам о загрузке нужен срок годности. Очередь должна иметь ограничение; при исчерпании ёмкости запрос получает явный отказ с возможностью повторить его отдельной попыткой. Повторы не скрываются в статистике. Для настоящего inference engine дополнительно проверяются TTFT, длина decode, использование KV-cache и стоимость передачи состояния.

История диалога должна приходить в запросе либо храниться во внешнем хранилище. После потери A новая реплика получает полную подтверждённую историю и восстанавливает контекст; локальный кеш заново вычисляется. Идентификатор сессии не заменяет историю. Уже начатый поток остаётся на A до завершения или явной отмены в пределах grace period. Переносить середину потока на B без протокола продолжения нельзя: после обрыва клиенту сообщается ошибка, а повтор получает отдельный request ID. В данном стенде автоматическое продолжение оборванного потока не реализовано.

Это соответствует кейсу Google Cloud из лекции 11, слайд 70, около 08:20 видео. В первичном описании Vertex AI/GKE Inference Gateway учитываются и содержимое запроса, и загрузка; для горячих префиксов усилен вес очереди и используется admission control. Результаты Google относятся к их production-нагрузке и не переносятся на этот CPU-имитатор. Здесь проверяется более простое исправление: убрать постоянную ClientIP-привязку и подтвердить эффект повторным одинаковым сценарием.
